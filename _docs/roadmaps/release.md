# Release

Один документ на випуск: порядок, контракт дистрибуції і те, що в цей випуск не входить. App і Site лишаються своїми роадмапами. Тут вони сходяться.

Мета: чужа людина ставить Fleet на Mac, бачить своїх агентів і доводить одну задачу до кола з Manager. На сайті лишається Early access.

Один публічний репозиторій App (`eggs-gd/fleet.eggs.gd`) тримає код, лендінг у `site/` і GitHub Releases. Окремого репозиторія сайту немає. Бінарники в git не живуть.

## Порядок

1. [App](app.md) закриває локальний API. До цього публічний бінарник не виходить.
2. [App](app.md) збирає `darwin/arm64` з UI всередині, за контрактом нижче.
3. Той самий workflow публікує Release у репозиторій App. Команда встановлення на сайті починає ставити цей архів.
4. [App](app.md) канал подій у сесію Manager. Шина і канал `task` зроблені раніше за крок 1.
5. Early birds ставлять цей бінарник і проходять шлях без пояснень.

Лендінг уже показує петлю Manager, див. [site](site.md). Публічний бінарник усе одно не виходить, поки крок 1 не закриє дірку `127.0.0.1:8787`. Linux і «є новіша версія» йдуть слідом за першим асетом. Ставлять так: людина копіює команду, `install.sh` забирає архів і кладе бінарник у `~/.local/bin`, бінарник піднімає сервіс і відкриває браузер. Окремої кнопки Download немає. Windows не входить, див. [windows](../specs/windows.md).

## Контракт

Semver: `v0.0.x` ранні збірки, `v0.1.0` перший публічний реліз, `v0.x` з дозволеними breaking changes, `v1.0.0` коли контракт устаканиться.

Асет, який упізнає `install.sh` (`darwin|macos` і `arm64|aarch64`; інакше він вважає файл amd64):

```text
fleet_0.0.1_darwin_arm64.tar.gz
checksums.txt
```

Перший Release містить лише `darwin/arm64`. Linux — наступний таргет. Windows-асет не публікуємо: скрипт його не пропонує.

### App

**немає**, крім зашитої версії `0.0.1` і збірки, яку розробник запускає сам.

- UI вбудовано в бінарник. Зараз `go:embed` тягне лише стартовий шаблон, а інтерфейс береться з `--backoffice-dir view/dist`.
- Версія з тега через `-ldflags`, не константа в коді.
- Тег `v0.0.x` у App збирає `view`, потім Go, пакує архів і `checksums.txt`, публікує Release у цей самий репозиторій.
- Нотатки релізу генерує workflow App. Лендінг лежить у `site/` того самого дерева.
- Бінарник за замовчуванням піднімає сервіс, чекає готовності, відкриває браузер і лишається жити. `make serve` у шлях користувача не входить. Прапорець без браузера лишається для headless.

### Site

**частково.**

- **частково.** Лендінг живе в `App/site`. Pages збирає його workflow з кореня App. На сторінці ще кнопка Download: вона читає `releases/latest` репозиторія App і без асетів показує Coming soon. Її замінює поле з командою.
- **немає.** Сам Release. Його створює App.
- **немає.** `install.sh` і `uninstall.sh`, і поле з командою на сайті. Скрипт не знає версію: OS/arch → latest asset → checksum → `~/.local/bin` → запуск. Команда на сторінці лише викликає цей скрипт.

### Оновлення

**немає.** Fleet знає свою версію, дивиться latest Release і каже, що є новіша. Завантаження, заміна файлу і перезапуск сюди не входять.

## Залежності людини

Не код репозиторіїв.

- Fine-grained PAT або GitHub App із `contents: write` на Site, секрет у App. `GITHUB_TOKEN` з App пише лише в App.
- Apple Developer ID і нотаризація. Без них Gatekeeper блокує бінарник, який ставить скрипт. Власна машина для early birds може йти раніше.
- LICENSE, EULA або Terms, Privacy і дисклеймер товарних знаків на Site до публічного анонсу.

## Не входить

Це не ТЗ. Інтерфейси App не повинні робити ці речі болючими потім.

- **Project Memory.** Шар поверх локального workspace: `tasks/`, `context/` (`state`, `decisions`, `constraints`, `architecture`), `handoffs/`. Після задачі — структурований handoff для наступного worker-а, без chain-of-thought.
- **Plane.** Лишається adapter. Канонічне сховище задач локальне, у Fleet. Двосторонній sync породжує ID, конфлікти і власність.
- **Practices / content.json.** Статичні нотатки на Site, які Fleet колись покаже через канал подій Manager. Тип `practice.available` канал має прийняти пізніше, див. [app](app.md).
- **Кілька інсталяцій одного провайдера.** `CODEX_HOME` і `CLAUDE_CONFIG_DIR` дають окремі акаунти на одній машині. Модель на потім: provider → installation → worker. Спочатку звірити це з правилами seat/usage.
- **ChatGPT Web як Manager.** Окремий тунель до локального MCP. Manager уже визначений як сесія наявного агента, див. [app](app.md).
- **Кластер і кілька хостів.** Спочатку логічні workers на одній машині, потім залізо.
- **Власна модель Manager, свій чат, Responses API.** Manager — чужа сесія.
- **Складний updater.** Канали, rollback, delta. Для цього випуску достатньо «є новіша версія».
- **DRM і obfuscation.**
