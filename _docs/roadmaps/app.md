# App

Fleet координує Codex, Claude Code, Cursor і людину. Fleet не є ще одним coding agent. Manager — не модель всередині Fleet. Це виділена сесія агента, якого людина вже використовує.

## Цикл

**частково.** Прямий хід (задача, worker, `needs_review`) у App є. Події `task.needs_attention` і `task.needs_review` пишуться в audit і публікуються на шині. Manager читає їх через `manager_events`, у сесію їх ніхто не штовхає. Відповідь людини в сесії Manager і подальше продовження worker-а цим каналом не вимірюються.

```text
rough human intent
        ↓
     Manager
        ↓
structured task / dependencies
        ↓
     Fleet
        ↓
native worker
        ↓
Running
        ↓
Needs Attention / Needs Review
        ↓
     Manager
        ↓
      Human
        ↓
worker continues
        ↓
review + Accepted
```

Manager бачить проєкти, задачі, залежності, статуси, workers, blockers, ownership і review state через Fleet/MCP. Доступ до filesystem йому не потрібен. Сховище стану (markdown сьогодні, інше завтра) для Manager невидиме.

Якщо задача ще не готова до імплементації, Manager створює окрему research-задачу, яка блокує імплементацію. Специфікацію він не вигадує.

- **готово.** Manager API і MCP на локальному сервері.
- **готово.** Статус `needs_review` і продовження роботи після нього.
- **готово.** Шина подій. Канал `task` публікує `task.needs_attention`, коли задача стає `blocked` (запуск не вдався, timeout, orphan) і коли worker ставить питання: пауза лишає статус `doing`. `task.needs_review` — коли робота готова до review. Канали `release`, `worker`, `practice`, `configuration` названі, видавців немає. Візуалізація стрічки — наступний крок.
- **готово.** Manager — сесія Claude, Codex, Cursor або Gemini з коренем data root. Для Claude, Codex і Gemini Fleet створює сесію і пам’ятає identity. Для Cursor Fleet не запускає процес: Manager — це ця папка, відкрита в Cursor. З телефона Cursor-сесія не видна. Розмова живе в додатку провайдера. Fleet у сесію Manager не пише: `send_message_to_thread` з `codex-app-tools` живе всередині Codex Desktop, і зовнішній процес до нього не підключений.

Manager бачить дошку через Fleet MCP у рідному конфігу свого провайдера. Людина відповідає в додатку провайдера. Manager через MCP оновлює задачу, worker продовжує.

Пізніше той самий `Publish`, без нової схеми доставки: `worker.offline`, `worker.quota_low`, `release.available`, `practice.available`, `configuration.recommended`. У цей випуск вони не входять.

## Ownership

**готово** як інваріант. Один агент, один репозиторій, одна активна задача. Різні репозиторії йдуть паралельно. Один репозиторій серіалізований.

```text
Running         → ownership HELD
Needs Attention → ownership HELD
Needs Review    → ownership HELD
Accepted        → ownership RELEASED
```

Blocked і Needs Attention не є завершенням. Зупинена сесія не є прийнятою роботою. Наступний worker отримує репозиторій лише після Accepted.

## Activation

**немає** як вимірювана подія. Подія задачі є на шині, але в сесію Manager не доставляється. Коло для сторонньої людини все ще не замкнене, поки людина не відповідає в додатку провайдера і worker не їде далі до Accepted.

## Робота, а не код

**частково.** Теза: Fleet керує роботою, а не артефактами. Задача живе у Fleet, робота відбувається у workspace: теці з кодом, документами, дослідженням або чим завгодно, з чим може працювати агент чи людина. Задача для людини артефакту не потребує. Репозиторій не є фундаментальною одиницею. Особисті концепції оператора (окремий простір, ім'я людини) — конфігурація його data root, не продукт.

Виконавцем може бути `unassigned`, агент (`claude`, `codex`, `cursor`, `gemini`) або людина, для якої є `Fleet/<ім'я>.md`. Автор коментарів людини — `owner`.

Ref задачі — `<ТЕГ>-<номер>`. Тег проєкту лежить у frontmatter `PROJECT.md`. Сканер генерує його для проєкту без тегу: чотири літери з id (перші літери, ініціали, приголосні), а коли вони зайняті, детермінована послідовність із seed від id. Тег можна змінити вручну (2–6 великих літер чи цифр, унікальний, не `INBOX`). Дублікат чи хибний тег сканер не чіпає, а показує в `degraded`. Лічильники окремі на кожен тег. Наявні ref-и лишаються валідними. Plane-проєкт відповідає рівно одному проєкту Fleet (`taskProvider.coreProject`), і нові задачі отримують ref з тегу цього проєкту. Якщо тегу немає, створення задачі падає з поясненням. Кілька Plane-проєктів на кілька проєктів Fleet: **немає**, див. [обмеження Plane](../PLANE_TASK_PROVIDER.md#limits).

Ще не перевірено на практиці: workspace без git і без репозиторію. Сканер знаходить лише git-checkouts, а запуск має repository gate. Це має показати експеримент: дати агенту Markdown-workspace і задачу «напиши статтю».

## Fleet веде роботу, а знання живе в проєкті

**готово.** Fleet керує лише роботою: задачами, воркерами, чергою, ревʼю. Знання про проєкт (структура, концепції, рішення) лежить у репозиторії проєкту, у його документації. Друге джерело правди в Fleet застаріває, його ніхто не оновлює, воно не привʼязане до задач і його ніхто не обслуговує. Рішення, потрібне для однієї задачі, лежить у картці цієї задачі.

Що з цього випливає:

1. **готово.** Проєкт не має тек `notes/`, `decisions/` і `inbox/`. Сканер їх не створює, а в `manager_project` лишився лише alias, тепер це `manager_alias(project, alias)`. Вид `note` і `decision` прибрано з інструмента, схеми, skill `intake` і документів шаблону. Глобальний Inbox лишається: це сирий ввід.
2. **готово.** `PROJECT.md` описує лише те, чим керує Fleet: id, title, tag, aliases, default_assignee, звʼязок з репозиторіями і один абзац опису, за яким Manager упізнає проєкт. Таблиця репозиторіїв, стек, звʼязки, захист і «Technology Evidence» описували структуру проєкту й застаріли б, тому сканер їх більше не пише. Профіль репозиторію лишається похідним станом, який сканер перераховує.
3. **готово.** Задача має власні розділи: Request, Acceptance Criteria і Context (лише коли є що додати). `manager_command` приймає `description`, `acceptance_criteria` і `context` окремими полями, а `source_inbox` потрапляє в frontmatter. Картки більше не мають Raw Input (сирий текст лишається в Inbox), Project Resolution, Deliverable і Handoff. Skill `shape-task` каже записувати причину, обмеження й ухвалені рішення в `context`, бо воркер бачить лише задачу. Якщо рішення має пережити задачу, Manager додає критерій «задокументувати вибір у документації репозиторію».
4. **готово.** Документування не окрема задача, а інструкція воркеру в тому ж проході. Промпт каже: якщо зміна робить хибним документ репозиторію, оновити його в тій самій зміні; рішення, потрібне тому, хто підтримуватиме код, записати там, де репозиторій уже тримає такі речі; нової структури документації не вигадувати. Проєкт без репозиторію чи документації цього правила не потребує: там документ і є результатом.
5. **готово.** Skill `review` питає, чи оновлено документи, які ця зміна зробила хибними.

### Що воркер отримує в запиті

**готово.** Воркер працює в цільовому репозиторії й не бачить data root, тому промпт не називає жодного файлу поза репозиторієм. Оркестратор сам збирає задачу (`tasklifecycle.WorkerBrief`): запит, критерії приймання, контекст і коментарі рецензії, які лишили люди. У промпт не потрапляють сирий ввід, технічні коментарі Fleet (chat id, команди resume, шляхи `/Users/…`), журнал, службові розділи й шляхи до data root. Промпт прямо каже, що файлу задачі в репозиторії немає, редагувати його чи створювати не треба, а результат іде JSON-ом. Коментарі Fleet тепер мають автора `fleet` (старі картки з `core` читаються так само).

### Куди дівається сире формулювання

**готово.** Одне постійне місце: `Inbox/items/*.md`. `intake` викликає `manager_inbox capture` перед будь-яким новим вводом, який стає роботою — незалежно від того, чи результат «задача», чи «Inbox». Раніше пряме створення задачі (`manager_command kind=task`, без проходу через Inbox) не мало де тримати сире формулювання, і сама інструкція «Always keep the raw wording» суперечила коду: розділу `## Raw Input` на картці задачі вже нема.

`promoted_to` на капчурі — список, не одне значення: коли один ввід розкладається на кілька задач, кожен `manager_command`/`promote` з тим самим `source_inbox` дописує ще один ref, а не замінює попередній. Задача, своєю чергою, показує `source_inbox` (`manager_task`), тож зв'язок видно в обидва боки. `manager_inbox list` дає огляд усіх капчурів (статус, перший рядок, які задачі постали), `manager_inbox show ref=INBOX-N` — повний текст одного й повний список його задач. Дашборд цього не показує: перегляд Inbox лишається розмовою з Manager, окремого екрана не будуємо.

### Відкрито

Ще не вирішено, і кожен пункт змінює обсяг роботи. Про опис проєкту й шину подій — див. нижче: обидва зроблені.

- **Задачі цілком у БД.** Зараз статус картки лежить у файлі, а сесії й події в БД, повʼязані ключем `task_ref`. Це два джерела правди: звідси `runtime_orphan_detected`, guard проти редагування картки під активну сесію, звірка після рестарту та дрейф лічильників. Якщо задачі, коментарі, лічильники, Inbox і картки проєктів переїдуть у БД, зникають Markdown-провайдер, файловий watcher, генерація `INDEX.md` і розбір frontmatter. У файлах лишаються тільки інструкції та конфігурація: `AGENTS.md`, skills, MCP-конфіги, `Fleet/*.md`. Ціна: історія й синхронізація задач через git зникають, потрібні міграції схеми БД і команда експорту. Рішення залежить від відповіді, чи потрібна оператору історія задач у git і синхронізація між машинами.
- **Похідний стан у БД.** `_registry/repositories.json`, `project-groups.json`, `deletion-candidates.*`, `bootstrap-report.md` і локальні налаштування (`core.local.yaml`) пише лише Fleet, читає лише його код, і там абсолютні шляхи машини. Якщо задачі йдуть у БД, це їм по дорозі. Інакше можна їх перенести окремо.
- **`Work/INDEX.md`.** Генерується лише для людини, а людина його руками не читає. Прибирається разом із генерацією (`fleet rebuild-index`, рядок у промпті воркера, згадки в шаблоні).

## Manager: skills, код і MCP

**готово.** Skills, MCP-інструменти і розкладання `MANAGER.md`. Спека: [manager-skills](../specs/manager-skills.md).

Канон skills — `.agents/skills/<name>/SKILL.md` у data root. Текст зашитий в App. Provisioning пише його на старті `serve` і разом із Fleet MCP. Файл, що відрізняється від зашитого, замінюється без копій. Збій запису зупиняє `serve` при старті: Manager без skills не має сенсу. Під час роботи збій не вбиває процес, а потрапляє в `/api/health` як `degraded`. Claude, Codex і Gemini отримують у своїй теці stub із вказівкою на канон (одне джерело), Cursor — правило. Cursor: `.cursor/rules/manager-<name>.mdc`, `alwaysApply: false`. MCP prompts із тими самими іменами читають канонічний файл. `AGENTS.md` для Manager каже три речі плюс шлях до skills. `_docs/MANAGER.md` у шаблоні — довідка на кілька десятків рядків: що кому належить і де лежать файли. Правила статусів і Definition Of Done лежать у `TASK_LIFECYCLE.md`, який читають і worker-и.

Події в сесію не пушаться. `manager_events(since)` читає рядки `task.*` і `project.*` з audit за id. Подія пишеться в audit до шини. Збій запису не скасовує зміну задачі, але видно в `degraded` і в `warnings` `manager_events`. Сканер (`Scanner.Watch`) сам створює й лагодить картки проєктів та лічильники, а не інструменти Manager.

## Опис проєкту пише Manager

**готово.** Сканер не має моделі, тож стартовий опис (абзац під заголовком картки) пише Manager, а не сканер. `manager_project_facts(project)` — лише читання: поточний опис, `summary_source` (`generated` — здогад сканера, найчастіше нічого не вартий для групи типу «Workspace group containing N repositories under `X/`»; `confirmed` — підтверджений), і README проєкту (кожного репозиторія — для групи). Manager пише абзац своїми словами, **показує людині і чекає «так»**, і лише тоді `manager_describe(project, summary)` записує його й ставить `summary_source: confirmed`. Сканер більше цей абзац не чіпає (як і aliases). Разом з `manager_alias` це єдине, що Manager пише на картці проєкту.

## Шина подій для проєктів

**готово.** Канал `project` поруч із `task`. Сканер (`Scanner.Watch`, кожен тик) публікує лише переходи, не стан: `project.discovered` (нова картка), `project.repos_changed` (список репозиторіїв справді змінився — не будь-який ремонт картки: формат aliases теж лагодиться, але це не подія), `project.missing` (проєкт зник із реєстру; картку **не видаляємо**, Ground Rule 5). Присутність проєкту рахується лише в памʼяті сканера, edge-triggered: проєкт, уже позначений відсутнім, вдруге не приходить, і проєкт, якого не було ще до старту `serve`, теж не приходить. Опис хеша README (пункт «чи змістовно змінився README») свідомо не робили: discovered + repos_changed + missing достатньо для першої версії.

Курсора на сервері для Manager нема: замість цього `AGENTS.md` каже перевіряти `manager_events` на кожному ході, з останнього баченого id (0 на новій сесії) — модель тримає це сама, в межах своєї розмови. Дашборд про ці події не знає, це розмова з Manager.

1. **готово.** `manager_board`, `manager_task` і skill `intake`.
2. **готово.** Поля `depends_on`, `repositories`, `acceptance_criteria`, `context`, `source_inbox` в `Intent` і `manager_validate`. Однина `repository` лишається. Default priority (5) і допустимі статуси описані в JSON Schema.
3. **готово.** `manager_resolve_project`, `manager_similar`, `manager_route`. Правило маршруту в коді: явна вказівка, `default_assignee` в `PROJECT.md`, Claude, вільний backup. `Fleet/ROUTING.md` лишається довідкою для людини.
4. **готово.** `manager_inbox`, `manager_alias`, `manager_workers`.
5. **готово.** `manager_answer`, `manager_review`, `manager_update` (зміна існуючої задачі), пагінація дошки з `detail=summary`, повний опис у `manager_task` і решта skills. Декомпозицію в один крок не закладено: після research зазвичай виходить багато задач. Цикл research → декомпозиція → створення — окремий крок.

Захист порту для цих записів уже є, див. крок 1 нижче.

## Порядок

1. **готово.** Локальний API на `127.0.0.1:8787` приймає лише `Host` `127.0.0.1`, `localhost` і `[::1]` зі своїм портом, відхиляє чужий `Origin`, вимагає токен запуску на `/api` і `/mcp` і не бере тіло не-JSON. Порожній POST і аудіо `multipart` лишаються. Токен один на інсталяцію: лежить у `~/.fleet/launch-token` (0600), створюється раз і переживає перезапуск, тож відкриті вкладки й сесії Manager не ламаються. У консоль він не друкується. Дашборд читає його з `<meta>` (сторінка йде з `no-store`), Fleet MCP отримує його в URL, тому в файлах конфігів провайдерів (`.mcp.json`, `.codex/config.toml`, `.cursor/mcp.json`, `.agents/mcp_config.json`) лежить цей токен. Це частина сетапу, файли трекаються. Токен стабільний, тож рядок міняється один раз, а не при кожному запуску. Він дійсний лише для `127.0.0.1` зі своїм Host, але в query потрапляє в логи, тож URL не публікувати. У dev `vite` проксі сам додає токен і Host. `POST /api/manager/session` і `POST /api/manager/adopt` під цим самим захистом: вони пишуть Fleet MCP і для Codex довіряють теку в глобальному `~/.codex/config.toml`.
2. **готово.** Шина подій. Канал `task`: `task.needs_attention`, `task.needs_review`. Інші канали без видавців.
3. **немає.** Збірка з [release](release.md): UI в бінарнику, версія з тега, workflow публікує `darwin/arm64` і checksums у цей самий репозиторій App.
4. **поза релізом.** [Windows](../specs/windows.md). Асет не публікувати.
5. Те, що не входить у випуск, зібрано в [release](release.md).

## Відоме, не в цьому випуску

**частково.** Запис Fleet MCP: невідомі ключі й чужі сервери зберігаються, битий JSON не перезаписується (помилка). Секцію TOML для Codex Fleet замінює власним редактором, а не парсером.
